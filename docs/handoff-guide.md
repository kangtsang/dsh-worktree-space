# 用 Worktree Space 派活

本文说明把一件跨仓库的工作交给一个任务空间会话（下文称「派活」）该怎么做，以及已知的坑怎么绕。

依据（**以实现为准**：本仓库构建产物 `lib/index.js`、`client/client.js` 与桌面端正在跑的
`~/.dsh/profiles/desktop/node_modules/dsh-worktree-space/` 同名文件 SHA256 相同，均为 1.2.2）：

- 全局工作规则 `~/.dsh/AGENTS.md` 第 8 节「Worktree Space 派活」——讲**为什么**，本文讲**怎么落地**；
- 本仓库 `src/host/task/`（`create.js`、`archive.js`、`delivery.js`、`tool.js`、`shared.js`）与构建产物 `lib/index.js`；
- 捆绑 skill `task-worktree-space`（面向 agent 的工作流说明，随包发布，位于 `assets/skill/task-worktree-space/SKILL.md`）。

交付与验收的细节（面板按钮、`deploy.yaml` 清单、状态文件契约、错误码速查、典型场景）已经在
[`delivery-guide.md`](delivery-guide.md) 里，本文不重复；设计原理与决策记录见
[`delivery-lifecycle.md`](delivery-lifecycle.md)。

---

## 1. 什么时候该用 / 不该用

**该用 Worktree Space 派活：**

- 一次改动横跨两个及以上仓库，需要这些仓库的改动同属一条分支、能一起合并回去；
- 需要**物理隔离**：任务空间的每个仓库都是一个独立检出，别的会话改不动同一批文件；
- 需要**独立验收**：一个隔离的部署环境、一个只属于本任务的验收地址，端口不与宿主已跑的服务冲突；
- 需要**独立分支**：分支名 `task/<任务名>`，不同任务的提交不会混在一条分支上；
- 需要**把事整块交出去**：一个会话在任务空间里跑完，另一个会话继续改别的东西。

本机的典型源根是 `D:\code\openapi`：该目录下并列着 9 个 git 仓库（`alpha-app-gateway`、
`alpha-bpm-gateway`、`alpha-cust-apikey`、`alpha-risk-trade`、`alpha-trade-common`、…），
一次要动其中两个以上时就是这一类。

**不该用：**

- 单仓库的小改动，改完就提交——直接在源仓库里改，省掉建空间、部署、收尾三件事；
- 只读代码、找一个结论、跑一次性的命令；
- 一件事一个人当场就能收尾，不需要别人按验收地址点一遍。

判断标准一句话：**需不需要一个与源检出物理隔离、能独立部署验收、能整支丢弃或合并回源仓库的目录。**
需要就建任务空间；不需要就在源仓库里改。

## 2. 一次派活的完整流程

整条链路是：**建任务空间 → 写任务书 → 部署与冒烟 → 面板验收 → 收尾 `done`**。
`deploy.target` 为 `none`（内置默认）时中间的部署与验收两步不存在，建完、干完、收尾三步即可。

### 2.1 先定三件事

| 要定的 | 工具参数 | 要点 |
|---|---|---|
| 任务名 | `task` | 同时是任务空间目录名与分支后缀。不能含 `/`、`\`、空格。分支名 = `branchPrefix` + 任务名，默认前缀 `task/`，所以默认分支是 `task/<任务名>`；任何一个选中仓库里已有该分支，`create` 直接拒绝（`E3001`），此时换任务名 |
| 源根 | `sourceRoot` | 放仓库的那个目录。该目录本身就是 git 仓库时直接作为源根；一个 git worktree 检出不能作源根 |
| 容器根 | `tasksRoot` | 任务空间放哪。先跑 `action: "suggest-root"`：报告该源根会横跨哪些仓库、推荐容器根（默认是根工作区下一级的 `worktree-space`，插件配置里若有固定答案则返回配置值）。容器根与源仓库目录**不得互相包含**，容器根自身有 `.git` 会被拒绝 |

任务空间的实际形状是 `<容器根>/<源根目录名>/<任务名>/<仓库名>`：中间那层是项目层，用源根自己的
目录名，作用是让两个项目下同名任务不互相覆盖。

### 2.2 建任务空间

用 `task_worktree_space` 的 `action: "create"`。该动作一次做完三件事：建任务空间目录、按
`branchPrefix` + 任务名建一条分支并为每个选中仓库切一个 worktree，再把结果**注册为 DSH 工作区**
（注册这件事决定任务空间是否出现在工作区列表里）。

| 参数 | 取值 | 说明 |
|---|---|---|
| `task` | 名称 | 见上表 |
| `sourceRoot` | 目录 | 见上表；`create` 与 `suggest-root` 都必填 |
| `tasksRoot` | 目录 | 省略则用推荐值；与源根互不包含 |
| `repos` | 仓库名数组 | 省略 = 源根下发现的全部仓库；只挑一部分时逐个列出 |
| `baseRef` | ref | 起点。省略 = 各仓库当前 HEAD。该 ref 必须在**每一个**选中仓库里都存在，缺一个就拒绝（`E3002`） |
| `branchPrefix` | 前缀 | 省略为 `task/` |
| `delivery` | JSON 对象 | 交付策略，见下表；**在创建时声明并随任务记录下来** |
| `deployScript` | 相对路径 | 源根内的一个现有文件，被复制成任务空间里固定名字的 `deploy/deploy.sh`，于是清单不用改而每个任务背后的脚本可以不同。绝对路径、源根之外的路径、不存在的文件都在创建前以 `E4014` 拒绝 |
| `registerWorkspace` | 布尔 | 传 `false` 时任务空间留在磁盘上但不进工作区列表，此时上面点名的工作区入口不存在 |
| `prompt` | 文本 | **任务书**。给了就同时在任务空间里开一个会话并把这段文本交给该会话（等价于面板的「创建并打开会话」再补一句），返回该会话 id |
| `permission` | 继承 / `workspace-write` / `danger-full-access` | 会话权限。默认继承调用方，**永远不会比调用方更宽**；`danger-full-access` 是整台机器可写、且不再弹审批 |

`delivery` 各字段（内置默认见 `src/host/task/delivery.js` 的 `DEFAULT_DELIVERY_POLICY`）：

| 字段 | 取值 | 默认 | 含义与影响 |
|---|---|---|---|
| `deploy.target` | `docker` / `host` / `none` | `none` | 验收载体。`none` 时**收尾闸门整体关闭**（`assertDeliveryGate` 在策略为 `none` 时直接放行）；`host` 默认禁止无人值守部署，需清单里 `autoAllowed: true` 显式豁免 |
| `deploy.mode` | `auto` / `on-request` | `on-request` | 无人值守部署是否允许自动发起 |
| `verification` | `agent` / `agent-then-human` / `human` | `human` | 谁签验收。`agent-then-human` 与 `human` 都要求面板点过「确认验收」（写入 `humanAck`）才放行合并 |
| `merge.mode` | `auto` / `ask` / `never` | `ask` | 谁按合并。`auto` = 收尾时不需要人确认，**只能由用户决定**；与 `human`／`agent-then-human` 互斥，同时给出会被 `E4010` 拒绝。`never` = 本流程不合并，`done` 传 `merge: true` 会被 `E4013` 拒绝 |
| `merge.target` | 分支名 | `null` = 各源仓库当前检出分支 | 合并落点。`done` 也可按次传 `target` |
| `merge.deleteBranch` | 布尔 | `false` | 合并后是否删任务分支；不删是可回退的一侧（任务空间没了以后，分支是这份工作唯一的记录） |
| `conflicts` | `agent-auto` / `ask` / `stop` | `ask` | 冲突怎么办。`agent-auto` = 用户已把「解决冲突 → 提交合并 → 再收尾一次」整段交给 agent，不必等面板按钮 |
| `strays` | `archive` / `keep` | `archive` | 未进 git 的生成物怎么办。`archive` = 复制进归档目录后从任务空间移除，一次收尾就能清完；`keep` = 留在原地并让收尾停下 |

建完后要拿到并交出三样东西：**任务空间目录路径**、**分支名**、以及被派单的**会话 id**。
任务空间在工作区列表里的入口是 `<源工作区标题>/<任务>`，也可以从面板的「创建并打开会话」打开。

任务已开工后才发现少了一个仓库：用 `action: "add"` 补，仓库用**绝对路径**列出（可以在别的源根、甚至
别的盘），新仓库会加入任务已有的那条分支。**不要为补一个仓库另建一个任务空间**，也不要手写
`git worktree add`。`add` 没有对应的「移除仓库」动作。

### 2.3 任务书

写一次就写完（原因见避坑清单第 1 条）。模板与逐项理由见 §3。

派单有两种入口，区别只在时机：

- `create` 带 `prompt`：建空间与派第一件活一次完成，适合「要有人把这件事做完」；
- `dispatch` 带 `prompt`：空间已经存在，派第二件及以后的工作。

**同一个任务空间不要再 `dispatch` 开第二个会话**——会出现两个都以为该干活的会话。要给在跑的任务会话
补话，用会话桥（见避坑清单第 11 条），不要新开会话。

### 2.4 部署与冒烟

任务空间可部署的条件（满足其一即可）：源根自带 `deploy/` 目录（创建时整份复制进来）、`create` 时用
`deployScript` 点名了一个脚本、或任务空间里自建了 `deploy/deploy.sh`（无清单时按仅 docker 的 L0 形态）。

要点：

- 每一次部署命令都要带该任务的 `DSH_ENV_ID`。值写在任务空间的 `worktree-space.md` 里，形如
  `DSH_ENV_ID=dsh-<项目>-<任务>`；这个 id 是容器、镜像、端口与验收地址互不干扰的依据，**不要猜、也不要复用别的任务的**。
- `up` 跑完写 `url`；`smoke` 跑完**合并**写 `lastSmoke`。**先让冒烟通过，再把地址交出去**：一个回 500 的地址不是交付物。冒烟失败的原因通常在该服务的日志里（`./deploy.sh logs <服务名>`）。
- 状态写到哪、怎么读，见 §4。

### 2.5 面板验收

面板的部署卡片每次实时查询，不缓存：验收地址、冒烟徽章、人工验收徽章、运行中容器数、刷新按钮。
操作按钮按状态出现：**部署验收**（容器不在时）、**执行冒烟**（容器运行时）、**确认验收**（冒烟通过且
未确认时）、**销毁环境**（容器运行时，两段确认）。改完代码的循环是：部署验收（重新打包）→ 执行冒烟 →
通过后确认验收 → 结束任务。验收事实（冒烟与人工确认）跟随任务空间：销毁环境不清除，重新部署保留。

**人工验收只能由人在面板点。** 工具侧没有签验收的参数：`done` 不带确认参数，`force` 直接以 `E7007`
被拒绝（判定为不可逆动作，必须由用户自己在管理页面做）。所以「这条任务不需要人验收」只有一个正当
表达——建空间时写 `merge.mode: "auto"` + `verification: "agent"`，而不是收尾时找路子绕过闸门。

### 2.6 收尾

由**持工具的会话或用户**执行（任务会话不该自己合并）。判据、参数语义与被拒后的处理见 §5。

## 3. 任务书模板

任务会话看不到派单方的会话，因此任务书必须**自包含**。下面整段可直接复制后填空。

```markdown
# 任务：<一句话目标>

## 0. 工作位置与纪律
- 工作目录：<任务空间绝对路径>（该目录本身不是 git 仓库，git 命令在各自仓库子目录里跑）
- 仓库：<仓库 A>、<仓库 B>；都在同一条分支 `task/<任务名>`
- 基线：<baseRef，或「各仓库当前 HEAD」>
- 禁止：在任何源检出里改文件或提交；`git push`（任何远端写操作）；手写 `git merge` 合并到源分支；
  `git reset --hard` / `git checkout .` 覆盖别人的未提交改动；删除与本次无关的文件

## 1. 要做什么
<逐条列出改动点：哪个仓库、哪个模块/文件、改成什么>

## 2. 验收标准（逐条可判定）
- <功能 A>：<点哪里 → 看到什么算通过>
- 接口：<curl 命令 + 期望状态码 / 关键字段>
- 回归：<必须仍然通过的东西，指明跑哪个命令>
- 判定口径：<数据从哪读、比对什么>

## 3. 隔离与验收栈（硬要求）
- 验收实例必须来自本任务空间。**禁止复用宿主的 dev server / 已经在跑的栈**：
  先检查 e2e 配置里的 `baseURL`、`webServer`、`reuseExistingServer: true`，命中就以本任务空间的地址为准，
  或者自带一份指向本任务空间的配置。
- 启动验收实例这类预计超过 1 分钟的动作丢后台或派子会话，不要占住主流程。
- 验收地址由脚本落盘，**直接读那个文件**，不要等命令输出的回传。

## 4. 交付状态必须落盘（硬要求）
- `deploy/deploy.sh up` 结束时把验收地址写进 `<任务空间>/deploy/.state.json` 的 `url`
- `deploy/deploy.sh smoke` 结束时把 `lastSmoke: { result, at }` **合并**写进同一文件，不丢已有字段
- 写这个文件**只用插件自带的 `deploy/write-state.sh`**：
  `./write-state.sh url <url>` / `./write-state.sh smoke pass|fail`；不要另带一份状态脚本
- **不要写 `humanAck` / `destroyedAt`**（插件所有：前者在用户于面板点确认验收时写入，后者在销毁时写入）
- 若任务空间里没有 `write-state.sh`（源根自带 `deploy/`，或用 `deployScript` 建的），脚本自己必须做上面这种合并写

## 5. 共享开发库的影响面与造数
- 本次是否改库结构：<否 / 是，改了哪些表与列，是否删列>
- 造数前缀：<如 `E2E-`、`ZZ_SMOKE…`，前缀与清理条件逐字一致>
- 清理：覆盖所有关联表；照仓库既有的清理脚本改（不要自己发明顺序）；清完给出**删前后数字**（删除条数、剩余行数）
- 有意留下的数据单独说明，不要混进「已清理」
- 影响面（若改了共享库）：**库新代码旧的栈一律会坏**（实测：菜单新增/编辑报 `Unknown column 'is_frame'`，
  而菜单列表看着正常）。合并后必须立刻重建宿主栈；本任务自己的部署环境也要重建

## 6. TODO 与回报（硬要求）
- 开工先 `todo_board` 一次写入整份计划（每条 `note` 写清验收标准），每完成一步立刻回写；
  **不要问用户「要不要用 TODO 板」**。若写入确实被审批门拒绝，改用会话内清单并在回报里说明，不要反复重试
- 回报节奏：每完成一个里程碑回报一次 + 收尾必须回报一次
- 回报方式：`wts_session_tool_send`（本插件自带的会话工具）发给父会话 `<父会话 id>`；
  有时效性的补话用 `mode: "steer"`，`queue` 只在回合边界被读到（见 §7 与
  [`session-tools.md`](../session-tools.md)）。第三方 `session_bridge_*` 工具若也装着，同样可用，
  但本插件这 8 个不依赖它：`wts_session_tool_find / _status / _read / _send / _create / _resume / _wait / _cancel`
- 收尾回报必含下面字段，缺一不算回报：
  `SMOKE=PASS/FAIL` 与计数、验收地址、点哪里看得到、提交 hash（每个仓库各一个）、**未覆盖/未验证部分**

## 7. 兜底与动态调整
- 任务侧不要在长时间构建 / 跑测试时空转：丢后台或派子会话，主流程继续
- 父会话另设的定时兜底只负责「回报没来」与「该收尾了」，不当作常规监控；间隔 30 分钟起，按进度调整

## 8. 收尾
- 判据：`deploy/.state.json` 里 `lastSmoke.result === "pass"`，且 worktree 无未提交改动
- 收尾由持工具的会话或用户执行；任务会话不要自己合并到源分支
- 被拒时把拒绝原文原样交回，**不要重试**
```

逐项为什么必须有：

| 段落 | 少了会怎样 |
|---|---|
| 0 工作位置与纪律 | 任务会话不知道源检出是只读参考，容易在源仓库里改；`push`、手写合并这类动作没有禁令就等于默认允许 |
| 1 要做什么 | 目标靠猜，做完的东西与预期不符，且没有判定依据 |
| 2 验收标准 | 「做完了」无法判定，回报只能自述，父会话只能再验一遍 |
| 3 隔离与验收栈 | 仓库自带 e2e 常把地址写死指向宿主在跑的那套，跑出来的「回归」验的是源检出（见避坑清单第 2 条） |
| 4 交付状态落盘 | 面板看不到地址、收尾被 `E5005` 直接拒绝（见 §4 与避坑清单第 3 条） |
| 5 共享库与造数 | 删列后「库新代码旧」的栈会坏；造数没前缀就清不干净，会留在共享库里 |
| 6 TODO 与回报 | 没有固定字段的回报无法核对；缺「未覆盖部分」会把没验的部分当成验过了 |
| 7 兜底 | 长任务无人看管；父会话只能靠猜进度 |
| 8 收尾 | 任务会话可能自己合并，或收尾判据不一致 |

## 4. 验收环境的地址与状态

**状态文件位置**：`<deploy 根>/.state.json`，`deploy 根` 是任务空间的 `deploy/` 目录。读取方会按顺序
找两处：`<任务空间>/deploy/.state.json`，以及 `<任务空间>/<仓库名>/deploy/.state.json`
（`src/host/task/deploy.js` 的 `deliveryStateFiles`）。找到一个能解析成 JSON 对象的就用它。

**字段（插件实际读的，写别的没用）**：

| 字段 | 谁写 | 含义 |
|---|---|---|
| `url` | 任务空间的部署脚本 | 验收地址。面板的「验收地址」显示这一项；销毁后置 `null` |
| `lastSmoke` | 任务空间的冒烟脚本 | 对象，至少要 `result` 与 `at`。**收尾要求 `result === "pass"`** |
| `humanAck` | 插件 | 用户于面板点「确认验收」时写入；脚本**不要写** |
| `destroyedAt` | 插件 | 环境销毁时写入；脚本**不要写** |
| `services` | 可选 | 服务清单，原始 JSON |

**写入方式**：只用任务空间里的 `deploy/write-state.sh`（该脚本由 `create` 脚手架写进任务空间的 `deploy/` 目录）：

```sh
./write-state.sh url http://localhost:22809    # up 跑完后，写验收地址
./write-state.sh smoke pass                    # smoke 跑完后，合并写入 lastSmoke（带 UTC 时间戳）
./write-state.sh services '[{"name":"web","state":"running"}]'   # 可选
```

这个脚本做的是**合并**：读出已有对象、只替换被点名的那一个顶层字段、再整份写回一行 JSON。
`humanAck` 与 `destroyedAt` 因此不会被抹掉。相反，一份自己写的状态脚本从零重写整个文件，就会把用户
已经点过的验收抹掉——所以**不要另带一份状态脚本**。

`write-state.sh` 并非无条件存在：它只在创建时任务空间**没有** `deploy/` 目录的情况下才被脚手架写入
（`src/host/task/create.js`：先把源根的 `deploy/` 整份复制进来，再把 `deployScript` 拷成 `deploy/deploy.sh`，
两步之后 `deploy/` 已存在就不再脚手架）。源根自带 `deploy/`、或用 `deployScript` 建的任务空间里，
合并写必须由那个脚本自己做。

**面板为什么可能看不到地址**：面板读的就是这个文件。文件缺失或字段缺失时，卡片只能显示「未冒烟」、
「部署状态没有记录验收地址」，容器一项则靠 `dsh.env-id` 标签查得到——看起来「环境在跑但什么状态都没有」，
根因是脚本没写状态。状态文件缺失时，若清单在 `targets.<目标>.status` 声明了命令，面板还提供
「从脚本读一次」，从该命令输出末尾的 JSON 里取 `url`/`URL`；这个地址会被标注为
「来自脚本的 status 输出，不是记录的状态」，**不能替代落盘的状态**（闸门读的仍是文件）。

**收尾闸门与状态的关系**（`assertDeliveryGate`）：

| 情况 | 结果 |
|---|---|
| 策略 `deploy.target` 为 `none` | 闸门整体关闭，`merge` 不校验状态 |
| 策略要求部署，但读不到状态文件 | `E5005`：收尾合并被直接拒绝 |
| 有状态，但 `lastSmoke.result` 不是 `pass`（且只缺这一项） | `E5006` |
| 缺项不止冒烟（例如同时缺人工验收） | `E5007`：策略在等人签，去面板确认，或由用户在面板的结束对话框里二次确认继续 |
| 状态齐全 | 放行 |

所以状态不是显示问题，而是**收尾路径的通行证**：读不到状态就没有合并且也没有可点的地址。

## 5. 收尾

### 5.1 判据

两条同时成立才收尾：

1. `deploy/.state.json` 的 `lastSmoke.result === "pass"`；
2. worktree 里**没有未提交改动**（`done` 会对每个仓库单独判断，有未提交改动的那个仓库会被留下并报告
   `uncommitted work is waiting in <路径>`，其余仓库继续）。

收尾前的两道检查也要知道：

- `done` 先做**可移除性探测**（把目录改名再改回来）：任何 worktree 被外部进程占着（从任务空间起的
  dev server、浏览器、编辑器）就报 `E5011`，**此时什么都还没合并、没删除、没归档**，关掉占用进程再收尾一次；
- 任务空间里必须有 `worktree-space.json`（插件创建时写的任务记录）。该文件被手工删掉时，`done` 会拒绝
  且不删除任何东西。

### 5.2 `done` 的参数语义

| 参数 | 语义 |
|---|---|
| `tasksRoot` + `task` + `project` | 定位任务：容器根 + 任务名 + 项目层（源根目录名）。**也可以只传 `sourceRoot` 代替 `project`**；两者都不传会被拒绝，因为容器根单独无法确定同名任务属于哪个项目 |
| `merge` | 是否合并。**只在用户明确说了要合并时才传 `true`**——除非任务自己的记录已经回答：`merge.mode: "auto"` 就是「这个任务自己合并」的常驻答复，此时不传 `merge` 也会合并；`merge.mode: "never"` 时传 `true` 被 `E4013` 拒绝，出路是用户自己在面板结束任务 |
| `target` | 合并到哪条分支，各仓库同一条。省略 = 每个源仓库当前检出的分支。指定的分支必须是源仓库的**本地分支**，否则 `E4008`；指向任务分支自己也 `E4008`。分支不在任何检出里时，会在临时 worktree 里合并，不动任何源检出 |
| `deleteBranch` | 合并后是否删除任务分支。**默认保留**；与 `merge` 同用。不合并只删分支属于「放弃任务」，需要 `force` |
| `cleanStray` / `keep` | 未进 git 的生成物：默认按任务策略（内置默认 `archive`：复制进归档目录后移除，一次收尾即可清完）。`keep` 列出必须原地保留的条目（例如用户自己的文档）；`cleanStray: true` 连构建产物一起清 |
| `conflicts`（任务策略） | `ask` / `stop`：合并前的预演遇到冲突就停下，返回 `mergeInProgress`、`mergeSite`（冲突所在的检出）与 `conflictedFiles`（冲突文件清单），由用户在面板把冲突交给 agent；`agent-auto`：用户已授权整段自动流程，解决冲突文件、在该检出提交合并、再带着同样的请求调一次 `done` |
| `force` | 丢弃未提交改动、强删未落地的分支。**工具调用一律以 `E7007` 拒绝**，只能在管理页面由用户操作 |
| `unregisterWorkspace` | 收尾把任务空间整个移除时，工作区注册也一并撤销，原本挂在该任务下的会话随之离开那个分组；传 `false` 才保留注册——注意此时目录已经不在磁盘上，工作区列表里会留一个指向已删目录的条目 |

合并前 `done` 会在任务空间的 worktree 里**反向预演一次**（`git merge --no-ff --no-edit <target>`）：
干净就把这次预演撤掉（`git reset --hard` 回预演前的 HEAD），冲突就把它留在原地并报告。源检出与目标分支
在这次预演里不动。

收尾成功后会自动销毁该任务的部署环境（`deploy.target` 不是 `none` 且记录了环境 id 时）：想让用户先看
验收环境，就在收尾之前看完。

### 5.3 被拒之后

被拒（`E5005` / `E5006` / `E5007` / `E5011` / `E2003` / `E4013` / `E4008` 等）时：

1. 把**拒绝原文**原样交给用户，不要改写成自己的话；
2. **不要原样重试**。闸门读的是状态文件，重试同样的调用只会拿到同样的拒绝；
3. 按拒绝点名的缺项走：缺部署状态就先部署、缺冒烟就先冒烟、缺人工验收就请用户在面板点；
4. 确实需要绕过闸门时，只能由用户在面板的结束对话框里二次确认继续：对话框会写明尚未完成冒烟验证和人工验收确认，继续则带确认合并并在日志里记一条 warning。agent 没有这个通道。

## 6. 避坑清单

前 15 条是实测踩过的；第 16～21 条由实现读出（`src/host/task/`），一并列出。

1. **派出去的会话不属于调用方，事后补不上话**
   - 症状：派完单再往那个会话发消息，报 `belongs to another parent session`（不属于本父会话）。
   - 原因：`create` / `dispatch` 开出来的会话挂在该任务空间下，不是调用方的子会话；`send_message` 只认自己的子会话。
   - 正确做法：**任务书一次写全**（§3 的模板整段照抄）。事后只能由用户在那个会话里、或面板上补话；跨父子要用 `wts_session_tool_send`。

2. **任务空间的验收栈与宿主栈是两套**
   - 症状：在任务空间里跑仓库自带的 e2e，看起来像一次真回归，实际上验的是宿主上那套、甚至源检出的 main。
   - 原因：仓库自带的 e2e 配置常把 `baseURL` 与 `webServer` 写死指向宿主已经在跑的栈，且 `reuseExistingServer: true`。
   - 正确做法：任务书要求任务空间**带自己的 e2e 配置**（指向本任务空间起的实例），或者**明确禁止复用宿主 dev server**；命中 `reuseExistingServer: true` 就以本任务空间的地址为准。

3. **交付状态必须由任务空间的脚本合并写入 `deploy/.state.json`**
   - 症状：面板看不到验收地址与冒烟状态（只剩靠 `dsh.env-id` 标签查到的容器），收尾合并被 `E5005` 拒绝。
   - 原因：插件自己不产生交付事实，只读那个文件；缺 `url` 或缺 `lastSmoke.result === "pass"`，闸门就不放行。
   - 正确做法：`up` 写 `url`、`smoke` 合并写 `lastSmoke`；**只用插件自带的 `deploy/write-state.sh`**（`./write-state.sh url <url>` / `./write-state.sh smoke pass|fail`），不要另带一份状态脚本——两个写手会互相覆盖或漂移。任务空间里没有该脚本时（源根自带 `deploy/` 或用 `deployScript`），脚本自己必须做合并写。

4. **`merge: auto` 是「这个任务不要人验收」的决定，只能来自用户**
   - 症状：为了省事替用户设了 `auto`，结果这条任务没经过人验收就直接合并回源分支。
   - 原因：`auto` 与「等人签的验收」互斥（同时给出会被 `E4010` 拒绝），而人工验收在工具侧签不了，只能由用户在面板点。
   - 正确做法：`auto` 只在用户明确表示该任务不需要人工验收时设置；其余情况留 `ask`，由用户在面板点「确认验收」。**不要用 `auto` 绕闸门**。

5. **收尾由持工具的会话或用户执行，任务会话不该自己合并**
   - 症状：任务会话自己把分支合并进源仓库，合并这个动作脱离了验收与闸门。
   - 原因：任务会话看不到任务空间之外的东西，也拿不到验收事实；合并是交付决策。
   - 正确做法：任务会话只干到「提交 + 回报」；`done` 由派单的会话或用户在面板执行。任务书里写清这条纪律。

6. **共享开发库与代码要成对上线**
   - 症状：实测宿主栈的菜单新增/编辑报 `Unknown column 'is_frame'`，而菜单列表却看着正常。
   - 原因：任务改了共享库的列（尤其**删列**）后，任何「库新代码旧」的栈都会坏——列表只读部分列看不出问题，写入路径才暴露。
   - 正确做法：合并后**立刻重建宿主栈**；任务书里写明这个影响面（改了哪些表、哪些列、哪一类栈需要重建），并让任务自己的部署环境也在合并后重建一次。

7. **造数要带可识别前缀，并在任务内清干净**
   - 症状：共享库里留下冒烟/验收数据，父表删了子表还在，越积越多。
   - 原因：靠人工记 id 的清单一定会漏；清理条件与造数前缀不一致就删不干净。
   - 正确做法：造数前缀写进任务书（如 `E2E-`、`ZZ_SMOKE…`），前缀与清理条件**逐字一致**；清理覆盖关联表，照仓库既有清理脚本的顺序写；清完给**删前后数字**；有意留下的数据单独说明。父会话收尾要**独立复查**一次，不能只看任务会话的自述。

8. **任务空间里不该有 junction / 符号链接**
   - 症状：收尾归档阶段报 `EPERM`（或归档没能完成、任务空间留下）。
   - 原因：归档是复制，而复制必须**重建**链接；本机普通安装（未开开发者模式）不能创建符号链接。链接又是指向别处的名字，插件不会把指向的内容复制过去。
   - 正确做法：任务空间里不要建链接；发现就把那些条目报给用户，由用户把条目移走或删掉（一个条目一次删除，不需要特权），再收尾一次。**不要自行删源仓库里的东西**。提示：当前实现会在归档前先探测本机能否建链接，探测到不能建就跳过链接、在 warning 里点名（`leftover-holds-links`）并把该条目留在原地，所以表现可能是「归档未完、任务空间还在」而不是抛 `EPERM`——两种都指向同一件事：链接必须在收尾前移走。

9. **一个任务空间不要再 `dispatch` 开会话**
   - 症状：两个会话都以为该干活，改同一批文件，提交互相打断。
   - 原因：`dispatch` 就是「在这个任务空间里再开一个会话」。
   - 正确做法：一个任务空间一个干活会话。补话用会话桥（第 11 条），补仓库用 `action: "add"`。

10. **任务会话的权限与 TODO 板**
    - 症状：把「板子可能用不了」写进任务书，任务会话于是跳过 TODO 板。
    - 原因：任务会话的权限来自调用方（`permission` 默认继承；传 `danger-full-access` 即整机可写、不再弹审批），在完全权限下 `todo_board` 的写操作照常通过；反过来，若**父会话**被设成「需要审批的操作一律拒绝」，被自动拒绝的是父会话自己的 `todo_board` 写操作。
    - 正确做法：任务书写「用 `todo_board` 一次写入整份计划」，不要写「板子可能用不了」。确实被审批门拒绝时才回退到会话内清单，并在回报里说明，不要反复重试。

11. **会话桥发消息分两种模式，长任务要用 `steer`**
    - 症状：给在跑的长任务发 `queue` 消息，迟迟没人读。
    - 原因：`queue` 只在该会话的**回合边界**被读取，而长任务整单常常是**一个长回合**，中途没有边界。
    - 正确做法：有时效性的补话用 `mode: "steer"`（打断当前回合注入一步）；`send_message` 只认自己的子会话，跨父子用 `wts_session_tool_send`。

12. **兜底定时只负责两件事，间隔要长**
    - 症状：把定时检查当成常规监控，频繁触发、频繁打断。
    - 原因：定时检查看不出「正在跑」与「卡住」的区别，密集轮询只会制造噪音。
    - 正确做法：兜底只负责「回报没来」与「该收尾了」，间隔 30 分钟起；按进度动态调整——接近完成 10～15 分钟，长时间构建或跑测试 30～45 分钟，卡住或同一处反复失败 10 分钟并附判断依据。查进度用会话桥看状态（是否 running、最后一次活动多久前、最后一句在做什么），必要时再读会话内容，**不要靠文件时间猜**。

13. **预计超过 1 分钟的动作丢后台或派子会话**
    - 症状：主会话停在启动验收实例上，用户发什么都只能等到下一轮。
    - 原因：启动实例（打包、装包、起进程、等端口）常在一分钟以上。
    - 正确做法：丢后台或派子会话，主会话立刻回到手上的活；**地址由脚本落盘，直接读那个文件**（不要等命令输出的回传——回传会被后续输出挤掉，而落盘文件可重复读）。

14. **本机两个 git / 文件系统坑**
    - 症状一：收尾后任务空间里只剩一个空目录。原因：本机的 `git worktree remove` 是**先注销再删目录**，删除失败时注册信息已经没了、目录还在。正确做法：收尾前关掉占用该目录的进程；`done` 会把这种仓库报告为「仍在磁盘上、需手工删除」，按报告删掉目录再收尾一次。
    - 症状二：某个「原样重建链接」的拷贝失败（`EPERM`）。原因：本机**可以建 junction，不能建符号链接**（创建符号链接需要特权，普通安装没有）。正确做法：凡是需要重建链接的动作都当作会失败来假设；发现有链接就报给用户，由用户移走。

15. **收尾判据与被拒后的处理**
    - 症状：被 `E5005` / `E5006` / `E5007` 拒绝后换个说法反复重试。
    - 原因：闸门读的是 `deploy/.state.json` 里的事实，重试同样的调用只会拿到同样的拒绝。
    - 正确做法：判据 = `lastSmoke.result === "pass"` **且** worktree 无未提交改动；被拒就把**拒绝原文原样交出**，按拒绝点名的缺项补，**不要重试**。

补充（由实现读出）：

16. **`deploy/write-state.sh` 不是每个任务空间都有**
    - 症状：任务书让脚本调用 `deploy/write-state.sh`，实际文件不存在。
    - 原因：该脚本只在创建时任务空间**没有** `deploy/` 目录时才生成；源根自带 `deploy/`（整份复制进来）、或用 `deployScript` 拷了脚本的任务空间都不会有。
    - 正确做法：任务书写清分支条件——有 `write-state.sh` 就用它；没有就由部署脚本自己做「读出已有对象 → 只替换被点名字段 → 整份写回一行 JSON」的合并写。

17. **`E5011` 是「有人占着目录」，此时什么都还没动**
    - 症状：收尾报 `E5011`，报错点名目录与占用原因。
    - 原因：`done` 先做可移除性探测（把目录改名再改回），改名失败即判定被外部进程占用。
    - 正确做法：关掉从任务空间起的 dev server、浏览器、编辑器，再收尾一次；探测本身不留痕，拒绝后任务空间与原来一样。

18. **收尾成功会自动销毁该任务的部署环境**
    - 症状：想让人再打开验收地址看一眼，地址已经没了。
    - 原因：`done` 走完且策略部署了东西（`deploy.target` 不是 `none`、记录了环境 id）时，会按 `dsh.env-id` 拆掉容器、网络与卷。
    - 正确做法：验收在收尾之前完成；确实要留着环境就先不收尾，由用户在面板「销毁环境」决定时机。

19. **任务名撞了分支、或空间已在磁盘上没注册时的两个拒绝**
    - 症状一：`create` 报 `E3001`。原因：`branchPrefix` + 任务名那条分支在某个选中仓库里已经存在。正确做法：换任务名。
    - 症状二：`create` 报 `E2002`。原因：同项目、同任务、同分支的任务空间**已经在磁盘上**，只是上次创建在注册为工作区之前停下了。正确做法：去面板把那个空间**注册**（面板上的「重新注册」按钮）后使用，不要换名重建——只要没处理，同名 `create` 会一直失败。

20. **仓库里的 `deploy/` 目录不等于插件的部署编排根**
    - 症状：以为某个仓库里的 `deploy/` 会被当作插件清单使用，实际没有。
    - 原因：创建时复制的是**源根**（`sourceRoot`）自己的 `deploy/` 目录；仓库内部的 `deploy/` 是那个仓库自己的东西。本机例子：`alpha-security-center\deploy\` 下是 `nacos`、`sql`，`alpha-risk-trade\deploy\` 下是 `nacos`、`tempo`，都不是编排根。
    - 正确做法：把 `deploy.yaml`（清单）与清单调用的脚本一起放进**源根**的 `deploy/`，之后每个新建的任务空间直接可用；只放清单不够，命令是相对该目录执行的。

21. **收尾默认是「归档」而不是「保留」**
    - 症状：收尾后任务空间里的构建产物、日志、临时文档都不在原地了。
    - 原因：内置默认 `strays: "archive"`——归档是**复制**到归档目录（默认 `<容器根>/archived-docs/<项目>/<任务>-<时间戳>/`）之后从任务空间移除，用户自己的文件不会被改写。
    - 正确做法：要原地保留的条目在 `done` 里用 `keep` 列出；要连构建产物一起清用 `cleanStray: true`；确实不想归档时把策略写成 `strays: "keep"`（收尾会停下来等处理）。

## 7. 给插件的优化建议

以下是本次实测与实现核对得出的限制，以及对应的插件侧建议。**这些是建议，不是已实现的行为**；
已经在跑的实现里确认支持的部分，逐条注明「现状」。

1. **派出的会话无法追加指令**
   - 现状：`create` / `dispatch` 开的会话不属于调用方，事后发消息报 `belongs to another parent session`，只能由用户在面板或那个会话里说。
   - 建议：给派活的父会话一条**受控的追加通道**（例如只允许补一条任务书附件）；或把「任务书一次写全」做成 UI 侧的强制校验（未勾选「回报机制 / 清理要求」不允许派单）。
   - 收益：任务书漏一条时不必把用户拉进面板。

2. **任务书三件套靠人手抄**
   - 现状：TODO 默认打开、回报节奏与固定字段、兜底与动态调整，每条任务都要重写一遍。
   - 建议：派活时注入一段**标准前言**（或提供可编辑模板），任务只填业务部分。
   - 收益：漏写概率直接归零。

3. **验收栈与宿主栈混淆**
   - 现状：仓库自带 e2e 常把 `baseURL` / `webServer` 写死指向宿主栈且 `reuseExistingServer: true`，跑出来的「回归」验的是源检出。
   - 建议：派活与收尾时**探测任务空间里的 e2e 配置**（命中宿主地址或 `reuseExistingServer: true` 即警告或拒绝），或强制要求任务空间自带 e2e 配置。
   - 收益：避免「看起来像真回归、其实验的是 main」。

4. **交付状态靠任务自觉上报**
   - 现状：面板**已经**显示冒烟徽章（冒烟通过 / 冒烟失败 / 未冒烟）、人工验收徽章（已人工验收 / 未人工验收）、以及状态文件缺失时的明确提示（「容器在跑，但脚本没有写交付状态：验收地址与冒烟无法显示，而且收尾合并会被拒（E5005）。」），所以「看不到状态」并非完全无提示。
   - 建议：把校验**前移**——在收尾前就提示缺 `url` / 缺 `lastSmoke`，而不是等 `done` 用 `E5005` 拒绝时才暴露；并让面板把「记录的状态」与「从脚本 status 读到的地址」在卡片上以更强的区分度呈现。
   - 收益：问题早暴露，不必等到收尾那一步。

5. **两个状态写手会漂移**
   - 现状：插件脚手架提供 `deploy/write-state.sh`，但任务里另带一份状态脚本就会互相覆盖（尤其抹掉 `humanAck`）。
   - 建议：只暴露一个写入口，并在缺失时给出明确提示（例如创建时就告知该任务空间没有 `write-state.sh`，需要脚本自己合并写）。
   - 收益：验收事实不会被一次「重写整个文件」抹掉。

6. **`merge: auto` 的后果不够显眼**
   - 现状：`auto` 是「这个任务不要人验收」的决定，与等人签的验收互斥。
   - 建议：UI 上做显式二次确认，把后果写清（不会等待人工验收、会直接合并回目标分支）。
   - 收益：避免为了省事而替用户降低验收门槛。

7. **共享库与代码成对上线这件事没有提示**
   - 现状：任务改了共享库的列（尤其删列）后，任何「库新代码旧」的栈都会坏（实测 `Unknown column 'is_frame'`），但插件不知道任务改过库。
   - 建议：跟踪任务内的结构变更脚本（例如 `docs/migrate-*.sql`、`**/sql/*.sql` 一类），收尾时提示「构建自 main 的栈需要重建」。
   - 收益：把只在合并后才暴露的故障前移。

8. **造数清理没有兜底**
   - 现状：造数前缀、关联表覆盖、删前后数字全靠任务书纪律与父会话复查。
   - 建议：支持一个**任务级清理契约**（约定的 `cleanup.sh`；把清理前后台账写进 `.state.json`），收尾时校验。
   - 收益：把「用完清除」从纪律变成机制。

9. **junction / 符号链接到收尾才处理**
   - 现状：收尾归档前会探测本机能否建链接，不能建就跳过链接、在 warning 里点名并留下条目（`leftover-holds-links`）。
   - 建议：把探测**前移到创建时**（并在任务空间里发现链接时立刻提示），而不是等到归档阶段。
   - 收益：链接类问题在开工时就知道，而不是收尾时才发现归档未完。

10. **`queue` 与 `steer` 的语义容易踩**
    - 现状：会话桥**已经**提供 `mode: "steer"`（打断当前回合注入一步），本环境可用；`queue` 只在该会话的回合边界被读取，而长任务常是一个长回合。
    - 建议：在会话桥的文档 / UI 上把两者差异讲清；若还要在插件面板内提供「给派出去的任务插话」的入口，目前**未在插件实现里检索到**这样的入口。
    - 收益：长任务中途的补话不再石沉大海。

11. **本机 git 版本导致的收尾残留**
    - 现状：本机的 `git worktree remove` 是**先注销再删目录**，删除失败时只剩目录；插件**已经**把这种仓库报告为「仍在磁盘上、需手工删除」（不是静默留下），但需要人再动手。
    - 建议：收尾时校验目录确实消失，未消失就在结果里单独点名（现状已覆盖），并考虑自动重试一次删除。
    - 收益：收尾结果更干净，少一次人工清理。

12. **状态一屏可见**
    - 现状：面板**已经**并列展示验收地址、冒烟徽章、人工验收徽章、运行中容器数与刷新按钮。
    - 建议：把「分支 / 领先提交数 / 最近一次会话活动」也并列进来，让「该不该收尾」一眼可判。
    - 收益：收尾决策不再需要另外查 git 与会话状态。

## 8. 附：与既有文档的差异，以及本文没有写成确定的部分
